HermesQA

HermesQA là bot tự động review pull request (PR) trên GitHub. Khi có PR mới, nó đọc phần code thay đổi, tìm lỗi bằng hai nguồn, rồi comment vào đúng dòng code có vấn đề. Nguồn thứ nhất là năm công cụ static analysis chạy trong một sandbox cô lập. Nguồn thứ hai là LLM đóng ba vai: kỹ sư phần mềm (SE), kiểm thử (QA) và vận hành (DevOps).

Hiện đang ở đâu

  • Đã xongPhần lõi chạy được từ đầu đến cuối ở chế độ offline qua dòng lệnh: đọc diff, quét static trong sandbox, LLM ba vai, lọc kết quả, sinh báo cáo.
  • Đã xongThực nghiệm trên 35 PR Python và 18 PR đa ngôn ngữ (JavaScript, TypeScript, React, Go, Java).
  • Dở dangHai lượt thực nghiệm mới nhất chưa commit và chưa đưa vào báo cáo. Bước gộp kết quả static với LLM đang làm tăng số báo nhầm.
  • Chưa làmChạy thử với GitHub App thật: toàn bộ nhánh webhook, hàng đợi, đăng comment lên PR chưa từng chạy đầu-cuối.

1. Dự án nhắm đến điều gì

Review code thủ công tốn thời gian của người có kinh nghiệm, chất lượng không đều giữa các reviewer, và người review dễ bỏ sót lỗi bảo mật khi đang tập trung vào logic nghiệp vụ. Hai cách tự động hoá hiện có đều thiếu một nửa:

  • Static analysis (semgrep, ruff…) rẻ và cho kết quả giống nhau mỗi lần chạy, nhưng chỉ bắt được các mẫu lỗi đã định nghĩa sẵn. Nó không biết thay đổi này thiếu test cho trường hợp nào.
  • LLM hiểu ngữ cảnh và nhận xét được về thiết kế, test, nhưng có thể bịa ra lỗi không tồn tại, báo sai số dòng, và tốn token.

HermesQA kết hợp cả hai, với ba điểm đồ án muốn đóng góp:

  1. Review theo ba vai. Mỗi vai có một bộ hướng dẫn riêng (checklist, thang mức độ nghiêm trọng, quy tắc chống nói thừa), và chỉ được gọi khi PR có loại file liên quan.
  2. Sandbox an toàn. Code trong PR đến từ người lạ nên không bao giờ được thực thi. Chỉ các công cụ static đọc nó, trong một container không có mạng.
  3. Chống LLM bịa lỗi. Bốn lớp kiểm tra xếp chồng, trong đó có bước self-verify: LLM tự kiểm chứng lại phát hiện của chính nó.

Giả thuyết cần kiểm chứng bằng thực nghiệm: kết hợp static với LLM cho kết quả tốt hơn dùng riêng từng nguồn. Số liệu hiện tại chưa ủng hộ giả thuyết này (xem mục 4).

Về lâu dài, README định hướng sản phẩm thành một micro-SaaS: hỗ trợ thêm GitLab và Bitbucket, dashboard web, học từ phản hồi của lập trình viên, nhiều khách hàng dùng chung và tính phí. Chưa phần nào trong số này được bắt đầu.

2. Luồng chạy từ A đến Z

Hệ thống có ba tiến trình: một API nhận webhook, một hàng đợi Redis, và một worker làm toàn bộ việc review. Worker gọi ra ba nơi: sandbox Docker, LLM, và cơ sở dữ liệu Postgres.

Mười một bước, theo đúng thứ tự trong mã

  1. 1

    GitHub gửi webhook khi PR thay đổi

    Khi một PR được mở, có commit mới, được mở lại, hoặc chuyển từ bản nháp sang sẵn sàng review, GitHub gọi POST /webhook/github kèm thông tin PR.

    Mục đích: bot tự chạy mỗi lần PR đổi, không ai phải bấm gì.

  2. 2

    API xác thực chữ ký rồi xếp việc vào hàng đợi

    app/main.py

    API tính lại mã HMAC SHA-256 trên nội dung nhận được bằng khoá bí mật chung với GitHub. Sai chữ ký thì trả 401. Sự kiện không phải pull request và PR còn ở dạng nháp bị bỏ qua. Phần còn lại được gói thành một job (repo, số PR, mã commit, mã cài đặt App) đẩy vào hàng đợi Redis, rồi API trả lời ngay.

    Mục đích: GitHub cắt webhook sau 10 giây, còn một lần review mất 1–3 phút, nên phần nhận và phần xử lý buộc phải tách nhau. Chữ ký HMAC chặn người ngoài giả làm GitHub để bắt bot chạy.

  3. 3

    Worker nhận job và báo "đang chạy" lên PR

    app/worker.py · app/github_app.py

    Worker lấy job khỏi hàng đợi (giới hạn 15 phút mỗi job). Nó ký một JWT bằng private key của GitHub App để đổi lấy installation token ngắn hạn, rồi tạo một check run tên "HermesQA Review" ở trạng thái in_progress.

    Mục đích: người mở PR thấy ngay bot đang làm việc. Token ngắn hạn chỉ có quyền trên repo đã cài App, nên nếu lộ thì thiệt hại có giới hạn.

  4. 4

    Clone đúng commit của PR, đọc cấu hình của repo

    app/worker.py

    Worker tải riêng commit đầu của PR với --depth 1, checkout, rồi gỡ remote khỏi thư mục .git. Sau đó đọc file .hermesqa.yml ở gốc repo nếu có: vai nào được bật, file nào bỏ qua, convention của team, số comment tối đa, có chặn merge khi gặp lỗi critical hay không.

    Mục đích: công cụ static và phần lấy ngữ cảnh cần file thật trên đĩa. Gỡ remote để token không nằm lại trong thư mục mà sandbox sắp đọc.

  5. 5

    Lấy diff và lọc file

    app/review/diff_utils.py

    Worker lấy diff của PR qua GitHub API và tách thành từng file. File khớp danh sách bỏ qua, file nhị phân và file bị xoá bị loại. Với mỗi file còn lại, hệ thống ghi nhớ những số dòng phía bản mới có mặt trong diff. Nếu không còn file nào, check run kết thúc success và dừng ở đây.

    Mục đích: mọi bước sau chỉ xét phần thay đổi. Danh sách số dòng này về sau quyết định comment được phép đặt ở đâu, vì GitHub chỉ nhận comment vào dòng nằm trong diff.

  6. 6

    Quét static trong sandbox

    app/sandbox.py · runner/run_static.sh · app/review/static_tools.py

    Worker ghi danh sách file thay đổi ra targets.txt rồi khởi chạy container hermesqa-runner. Bên trong, năm công cụ chạy lần lượt (semgrep, bandit, gitleaks, hadolint, ruff) và ghi kết quả JSON ra thư mục /out. Worker đọc các file JSON đó, chuẩn hoá về một cấu trúc chung gọi là Finding (file, dòng, mức độ, loại, mô tả, độ tin cậy), và chỉ giữ finding thuộc file thay đổi. Trạng thái từng công cụ (chạy được, thất bại, không áp dụng) được ghi lại để in ở đầu báo cáo.

    Mục đích: bắt các mẫu lỗi đã biết mà không tốn token, và cùng đầu vào thì luôn cho cùng kết quả. Sandbox bảo đảm một PR chứa mã độc không làm gì được hệ thống.

  7. 7

    Chọn vai cần chạy

    app/review/router.py

    PR có sửa code ứng dụng thì gọi SE và QA. PR có đụng tới file hạ tầng (Dockerfile, workflow CI, requirements, package.json, Terraform…) thì gọi DevOps. PR chỉ sửa tài liệu thì chỉ SE xem qua. Kết quả được giao với danh sách vai bật trong .hermesqa.yml.

    Mục đích: tiết kiệm token. PR chỉ sửa Dockerfile không cần hỏi vai QA.

  8. 8

    Từng vai review bằng LLM

    app/review/agent.py · app/skills/<vai>/SKILL.md

    Mỗi vai là một lần gọi LLM. File SKILL.md của vai làm system prompt. Phần câu hỏi gồm: tiêu đề và mô tả PR, convention của repo, ghi nhớ từ các lần review trước, tóm tắt những gì static đã bắt kèm yêu cầu không lặp lại, diff của từng file (tối đa 25 file) cùng 30 dòng xung quanh mỗi chỗ sửa có in sẵn số dòng, và một khuôn JSON bắt buộc cho câu trả lời. LLM trả về một câu tóm tắt và danh sách finding.

    Mục đích: bổ sung những thứ công cụ static không thấy được: lỗi logic, thiếu test, thiết kế kém. In sẵn số dòng và ép khuôn JSON để LLM khó báo sai vị trí và kết quả xử lý được bằng máy.

  9. 9

    Self-verify: LLM kiểm chứng lại chính nó

    app/review/agent.py

    Nếu một vai có finding, danh sách đó được gửi lại cho cùng model kèm code, lần này với lời dặn đóng vai reviewer cấp cao: bỏ finding không phải vấn đề thật, sửa số dòng lệch, bỏ finding trùng, cập nhật độ tin cậy. Nếu lần gọi này lỗi, hệ thống giữ kết quả ban đầu.

    Mục đích: giảm lỗi bịa. Đây là cơ chế được coi là đóng góp chính của đồ án, nhưng thực nghiệm chưa đo được lợi ích của nó (mục 4).

  10. 10

    Gộp, lọc và ra kết luận

    app/review/postprocess.py

    Finding của static và của LLM được gộp lại. Hai finding cùng file, lệch nhau không quá 2 dòng và cùng loại thì chỉ giữ một, ưu tiên bản của static. Tiếp theo là chính sách lọc: bỏ finding có độ tin cậy dưới 0,6 hoặc mức độ dưới medium; dòng được báo phải nằm trong diff (lệch tối đa 3 dòng thì kéo về dòng gần nhất); tối đa 15 comment gắn vào dòng, phần còn lại đưa vào danh sách phụ. Cuối cùng là kết luận của check run: failure nếu có lỗi critical và repo bật chặn merge, neutral nếu có lỗi critical hoặc high, còn lại success.

    Mục đích: PR không bị ngập comment, không có comment trỏ vào dòng không tồn tại, và team tự quyết bot có được chặn merge hay không.

  11. 11

    Đăng kết quả, lưu lại, dọn dẹp

    app/review/report.py · app/github_app.py · app/memory.py

    Worker sinh báo cáo Markdown đầy đủ, đăng một PR review gồm phần tóm tắt và các comment theo dòng (yêu cầu sửa nếu kết luận là failure, còn lại chỉ là nhận xét), đóng check run với kết luận ở bước 10, và lưu lượt review vào Postgres. Nếu GitHub từ chối comment theo dòng, worker gửi lại chỉ phần tóm tắt. Thư mục làm việc luôn được xoá khi kết thúc. Nếu có lỗi giữa chừng, check run đóng ở trạng thái neutral kèm thông báo lỗi, để bot hỏng không chặn nhầm việc merge.

    Mục đích: kết quả xuất hiện ngay tại nơi lập trình viên đang làm việc, và có lịch sử để tra lại.

Bốn lớp chống LLM bịa lỗi

  1. Ràng buộc đầu vào. Prompt in sẵn số dòng thật bên cạnh từng dòng code và yêu cầu chỉ báo dòng nằm trong diff.
  2. Self-verify. Lượt gọi thứ hai để loại finding sai và sửa số dòng (bước 9).
  3. Kiểm tra số dòng bằng mã. Finding trỏ vào dòng ngoài diff quá 3 dòng không được gắn comment, chỉ nằm trong danh sách phụ.
  4. Ưu tiên static khi trùng. Hai nguồn cùng báo một chỗ thì giữ bản của static.

Ngoài ra còn ngưỡng độ tin cậy 0,6 và trần 15 comment mỗi PR. Lớp 1, 3 và trần comment là kiểm tra tất định. Lớp 2 và lớp 4 là hai chỗ thực nghiệm cho thấy chưa hiệu quả.

4. Thực nghiệm và kết quả

Không có bộ dữ liệu chuẩn cho bài toán này nên đồ án tự sinh. eval/make_dataset.py tạo một repo Python sạch và 35 nhánh, mỗi nhánh cài đúng một lỗi đã biết (tổng 36 vị trí lỗi: 13 bảo mật, 8 DevOps, 7 bug, 4 test, 4 style và hiệu năng). Vị trí lỗi được tính tự động thành đáp án. eval/run_eval.py chạy HermesQA trên từng nhánh theo từng cấu hình, và eval/score.py so kết quả với đáp án.

Một finding được tính là đúng khi cùng file, lệch không quá 3 dòng và đúng loại lỗi so với một đáp án chưa được khớp. Mọi finding còn lại bị tính là báo nhầm, kể cả khi nó là nhận xét hợp lý nằm ngoài đáp án. Vì vậy precision ở đây là cận dưới. Khi chạy thực nghiệm, ngưỡng lọc của sản phẩm được nới hết để đo khả năng phát hiện.

Hai chỗ tài liệu và mã chưa khớp

  • Báo cáo và chú thích trong mã ghi webhook trả 202. Mã hiện trả 200, là mặc định của FastAPI. GitHub chấp nhận cả hai, nhưng nên sửa một trong hai cho thống nhất trước khi bảo vệ.

Pull request (PR)
Đề nghị gộp một nhóm thay đổi code vào nhánh chính, là nơi diễn ra việc review.
Diff
Phần khác nhau giữa bản cũ và bản mới của các file trong PR.
Webhook
Cách GitHub chủ động gọi vào hệ thống khi có sự kiện.
HMAC
Mã xác thực tính từ nội dung và một khoá bí mật, chứng minh webhook thật sự đến từ GitHub.
Check run
Dòng trạng thái hiện trên PR (đang chạy, đạt, không đạt). Có thể dùng để chặn merge.
Static analysis
Phân tích mã nguồn mà không chạy chương trình.
Sandbox
Môi trường cô lập để xử lý thứ không đáng tin.
Finding
Một phát hiện của bot: file, dòng, mức độ, loại lỗi, giải thích, gợi ý sửa, độ tin cậy.
Hallucination

Self-verify
Lượt gọi LLM thứ hai để kiểm chứng lại kết quả của lượt đầu.
Ground truth
Đáp án đã biết trước, dùng để chấm điểm.
Precision
Trong những gì bot báo, bao nhiêu phần là đúng.
Recall
Trong những lỗi có thật, bot bắt được bao nhiêu phần.
F1
Trung bình điều hoà của precision và recall. Chỉ cao khi cả hai cùng cao.
